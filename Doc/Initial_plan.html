01 Vision & positioning why this product, for whom

Product goal

  • Sellable, enterprise-grade education ERP + LMS
  • Multi-tenant SaaS first; single-tenant on-prem for enterprise tier
  • Serves schools, colleges, universities, coaching centres, online academies
  • Offline campus operations and online delivery in one data model

Learning goal

  • Cover the complete modern AI stack with real, shipped features
  • No toy demos — every AI feature runs on real tenant data
  • Each feature ships with an evaluation, not just a prompt
  • Built with an AI pair (Copilot / Antigravity) as the daily workflow

Differentiator

  • AI embedded inside every module, not a bolted-on chatbot
  • Campus data exposed as MCP tools — usable from any AI client
  • Grounded answers with citations and audit of AI decisions
  • AI credit metering as a first-class billing dimension

02 Tenancy & delivery model the shape of the data

Hierarchy

  • Group / Trust → owns many institutions
  • Institution → school, college, university, academy
  • Campus → physical or virtual location
  • Department → faculty / stream
  • Programme → course of study, credits
  • Batch → Section → Student

Delivery modes

  • Offline — attendance, transport, hostel, physical exams, campus ops
  • Online — LMS, live classes, online exams, proctoring, e-library
  • Hybrid — same student record, both channels, unified reporting
  • Every offline capability has an online equivalent where meaningful
Design rule: tenant ID is present on every row, enforced by row-level security — and the same rule applies to vector namespaces, object storage prefixes, cache keys and AI tool scopes.

04 Gap analysis & commercial opportunity why modules 29–64 exist

Tier A — deal blockers

These do not win deals. Their absence loses them. Every one of these has ended an enterprise education sale at the evaluation or security-review stage.
Gap Why you lose the deal
M60 Migration toolkit Every buyer already runs something. "How do we move eight years of data?" kills more deals than any missing feature
M62 Trust centre No SOC 2 / ISO 27001 / signed DPA means you are stopped at IT security review, every single time
M30 Gradebook & standards Exams alone are not enough — daily teaching lives in the gradebook
M49 Documents & e-sign Offers, consents and contracts are the paperwork of a campus
M57 Service desk Universities list the "one-stop student services shop" as a named requirement
M43 Health centre Mandatory in residential and K-12 institutions
M40 Visitor & gate security Child-safety requirement, and usually the first thing parents ask about
M47 Grievance & safeguarding Statutory in India (anti-ragging, POSH) and safeguarding law elsewhere
M31 Special education / IEP Legally mandated in the US, UK and Australia. Without it the entire Western market is closed
M64 Offline & edge node Rural India, Africa and South-East Asia do not have reliable connectivity
M63 White-label app Institutions want their app in the store, not yours

  • M29 Admissions CRM — rivals force a separate CRM purchase
  • M37 Campus card — one credential across every module wins demos

Backend

  • Java + Spring Boot + Spring AI, or
  • Python + FastAPI + LangGraph
  • Modular monolith first, services later

Frontend

  • React + TypeScript + Tailwind
  • Flutter or React Native for mobile
  • Design system from day one

Data & AI

  • PostgreSQL + pgvector, Redis, S3/MinIO, Kafka

Ops

  • Docker → Kubernetes, GitHub Actions
  • OpenTelemetry + Langfuse + Grafana
  • MLflow for models and experiments
Constraint that keeps this learnable: never let an AI capability live inside a feature module. It goes into the AI platform layer with a versioned prompt, a tool contract and an evaluation — then features consume it.

09 Platform, security & operations the 40% buyers never see — tick as you implement

Why this section exists: this product holds minors' identity, biometrics, health records, exam results and money. A feature bug is embarrassing; a platform failure during exam week or a cross-tenant data leak ends the company. Treat everything below as product work with its own backlog, not as "infra we will do later".

A · Observability

O01Logging

  • Structured JSON logs, one schema across services
  • Correlation ID and trace ID on every line
  • Tenant, user and module as standard fields
  • Log levels used consistently, no debug noise in prod
  • PII redaction at the source, never in the sink
  • Centralised aggregation (Loki / OpenSearch / ELK)
  • Retention tiers: hot 14 days, warm 90, cold 1 year
  • Sampling for high-volume paths
  • Audit log kept separate, append-only, tamper-evident
  • Per-tenant log scoping for support without data exposure

O02Metrics & SLOs

  • RED metrics per service: rate, errors, duration
  • USE metrics per resource: utilisation, saturation, errors
  • Prometheus + Grafana, dashboards per service and per tenant
  • Business metrics: logins, fee payments, marks published
  • SLIs defined for each critical journey
  • SLOs with error budgets, agreed with the business
  • Burn-rate alerting instead of raw threshold alerts
  • Cardinality control on labels

O03Distributed tracing

  • OpenTelemetry SDK in every service
  • Context propagation across HTTP, queues and jobs
  • Span attributes: tenant, user role, module, feature flag
  • Database and external-call spans
  • Tail-based sampling to keep slow and failed traces
  • Trace-to-log and trace-to-metric linking

O04Alerting & on-call

  • Alert only on symptoms users feel, not on causes
  • Severity levels with defined response times
  • Every alert links to a runbook
  • Deduplication, grouping and alert-fatigue review
  • On-call rotation, escalation policy, handover notes
  • Maintenance and silence windows
  • Monthly review: delete alerts nobody acted on

O05Frontend & synthetic monitoring

  • Uptime checks from multiple regions
  • Synthetic journeys: login, fee payment, mark attendance, publish result
  • Real user monitoring and Core Web Vitals
  • JavaScript error tracking (Sentry or equivalent)
  • Mobile crash-free rate and ANR tracking
  • Public status page fed by real checks

O06AI observability

  • Prompt and response traces with PII scrubbed
  • Token count and cost per tenant, feature and model
  • Latency and error rate broken down by model
  • Live evaluation scores and drift on production traffic
  • Hallucination, refusal and human-override rates
  • User feedback captured and linked to the trace
  • Alerts on cost spikes and quality regressions

B · Traffic, scale & performance

O07Edge & load balancing

  • DNS with health-based failover and low TTL
  • CDN for static assets, media and recorded lectures
  • Global load balancer, anycast, regional routing
  • WAF plus bot and scraper protection
  • L7 ingress, TLS 1.3 termination, HSTS
  • Health checks, readiness probes, connection draining
  • Avoid sticky sessions; keep services stateless
  • Blue-green traffic switching at the edge

O08Scaling & capacity

  • Horizontal pod autoscaling on real signals, not just CPU
  • Cluster autoscaler and node pools by workload type
  • Async workers and queues for heavy jobs
  • Scheduled pre-scaling for exam, result and fee-deadline peaks
  • Database read replicas and connection pooling
  • Partitioning or sharding by tenant for large tables
  • Hot-tenant detection and dedicated pools
  • Quarterly capacity review against growth forecast

O09Resilience patterns

  • Timeouts on every outbound call — no infinite waits
  • Retries with exponential backoff and jitter
  • Idempotency keys on payments and writes
  • Circuit breakers around third parties and model providers
  • Bulkheads so one module cannot starve the rest
  • Per-tenant rate limits and quotas
  • Queue-based load levelling and backpressure
  • Graceful degradation and feature kill switches
  • Dead-letter queues with replay tooling

O10Caching

  • CDN and edge cache for public and media content
  • Application cache in Redis with explicit TTLs
  • Cache keys always namespaced by tenant
  • Documented invalidation strategy per entity
  • Stampede protection and request coalescing
  • Semantic cache for repeated AI queries
  • Cache hit-rate monitoring

C · Reliability & continuity

O11Backup & disaster recovery

  • Automated backups with point-in-time recovery
  • Cross-region replication of data and object storage
  • Immutable, air-gapped copies to survive ransomware
  • RPO and RTO defined per data class
  • Tenant-level restore, not just whole-cluster restore
  • Restore drills on a schedule, with evidence recorded
  • Documented failover and failback runbooks
  • Backup encryption and separate key custody

O12Chaos & readiness testing

  • Load, soak and spike tests before every peak season
  • Chaos experiments: pod kill, latency injection, dependency failure
  • Game days with the on-call team
  • Dependency risk register with fallback per vendor
  • Performance budgets enforced in CI
  • Recovery time measured, not assumed

O13Incident management

  • Severity matrix with defined response and comms per level
  • Incident commander and scribe roles
  • Dedicated incident channel and timeline capture
  • Customer comms templates and status-page updates
  • Contractual notification deadlines tracked
  • Blameless postmortem within five working days
  • Action items owned, dated and verified closed
  • MTTD and MTTR tracked as engineering KPIs

D · Security engineering

O14Secure SDLC & supply chain

  • Threat model (STRIDE) written per module before build
  • Security requirements inside the module spec
  • SAST and linting on every pull request
  • DAST against staging on every release
  • Dependency and licence scanning (SCA)
  • Secret scanning on commits and history
  • Container image and IaC scanning
  • SBOM generated and stored per release
  • Signed artifacts and provenance attestation
  • Annual third-party penetration test
  • Vulnerability disclosure policy and SLA to patch

O15Access, secrets & keys

  • Zero-trust posture; no implicit network trust
  • Least privilege by default, reviewed quarterly
  • Just-in-time and break-glass production access, fully audited
  • SSO plus MFA mandatory for all staff
  • Workload identity instead of long-lived credentials
  • mTLS between internal services
  • Secrets in a vault or KMS, never in code or env files
  • Automated secret and certificate rotation
  • Separate keys per environment and per tenant tier

O16Data protection

  • Data classification: public, internal, confidential, restricted
  • Encryption at rest everywhere, TLS 1.3 in transit
  • Field-level encryption for PII, health and biometrics
  • Customer-managed keys for enterprise tenants
  • Payment data tokenised so PCI scope stays small
  • Biometric templates stored as irreversible vectors, never raw images
  • Masked or synthetic data in every non-production environment
  • DLP on exports, downloads and email
  • Documented data map: what we hold, where, why, for how long

O17Network & runtime

  • Private subnets; databases never publicly reachable
  • Egress allow-lists from production
  • Kubernetes network policies, default deny
  • Admission control: no root, no privileged, signed images only
  • Runtime threat detection on containers and hosts
  • DDoS protection at the edge
  • Bastion or session-manager access only, recorded
  • Honeytokens to detect credential theft

O18Tenant isolation assurance

  • Row-level security enforced in the database, not only in code
  • Tenant ID required on every query path, verified by test
  • Automated cross-tenant access tests in CI
  • IDOR and object-reference fuzzing on every endpoint
  • Vector namespace isolation verified per release
  • Object-storage prefix and signed-URL scope checks
  • Cache and queue key audits
  • AI tool calls scoped to the caller's tenant and role
  • Penetration test scoped specifically at multi-tenancy

O19Detection & response

  • SIEM with security events from all layers
  • Alerts on mass export, bulk download and unusual admin actions
  • Impossible-travel and credential-stuffing detection
  • Privileged action review workflow
  • Written incident response plan with named roles
  • Forensic readiness: log integrity and retention
  • Breach notification workflow inside statutory deadlines
  • Tabletop exercises twice a year
  • Cyber liability insurance in place

14 How to work through this the loop that keeps it moving

Per phase loop

  1. Pick exactly one phase from section 10 — never two.
  2. Write the module spec: entities, APIs, screens, permissions.
  3. Build the non-AI part first so the AI has real data to stand on.
  4. Add the AI feature behind a feature flag.
  5. Add its evaluation immediately — not later.
  6. Record what worked, what failed, cost, latency, prompt version.
  7. Refactor into a reusable AI platform capability.
  8. Demo the slice end to end, then move on.

Traps to avoid

  • Starting five modules and finishing none
  • Chatbot-first design instead of workflow-first
  • Skipping evaluation because "it looked right"
  • Fine-tuning before exhausting prompting and RAG
  • Letting tenant data leak across vector namespaces
  • Building AI features that cannot be turned off
  • Ignoring cost until the bill arrives
The single measure of success: at the end, you have one enterprise product you can sell — and for every AI topic in section 06, a real feature in that product you built, evaluated and can explain.
