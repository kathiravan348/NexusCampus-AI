# NEX-120 — Packaging: Helm chart for large self-hosted installs (product stack), images we already have

**Status:** planned · **Owner:** — · **Branch:** task/NEX-120 · **Depends on:** NEX-108

## Goal
A large institution installs the same product stack as `deploy/compose` on its own Kubernetes cluster with one chart:
same pinned images, secrets only from Kubernetes Secrets, restricted pods, default-deny network rules.

## Build
1. Services as Compose: `api`, `worker`, `web`, `migrate` (a pre-install / pre-upgrade Job, forward-only), and —
   each switchable to an external service — `db` (PostgreSQL), `keycloak`, `openbao`, `valkey`. Same image names and
   digests as `deploy/compose` (one place in `values.yaml`); no new image, no chart dependencies from the internet.
2. Secrets: only `existingSecret` names in values (never a secret value in `values.yaml`); the README shows how to
   create them; OpenBao init / unseal stays an operator step (as Compose), documented.
3. Pods: `runAsNonRoot`, `readOnlyRootFilesystem` where Compose has it, no privilege escalation, all capabilities
   dropped, seccomp `RuntimeDefault`, resource requests and limits, liveness / readiness from the Compose health
   checks, no `hostPath`, no `hostNetwork`, `automountServiceAccountToken: false`.
4. Network: default-deny `NetworkPolicy`; only web → api, api / worker → db, valkey, openbao, keycloak, and the agent's
   outbound HTTPS to `NEXUS_CONTROL_URL` (off when air-gapped). Optional Ingress (TLS from a named Secret).
5. Values schema rejects unknown keys and plain-text secrets; `helm lint` clean.
6. `test_helm_chart.py` runs `helm template` (skipped when `helm` is missing) and checks every rendered pod against
   step 3, the network policies against step 4, and that every image matches `deploy/compose`.

## Acceptance checks

  file) succeed; `test_helm_chart.py` passes.
