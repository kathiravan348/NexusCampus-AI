# NEX-133 — P04 offboarding, cell side (D61): freeze an institution, export it, destroy its keys on command

**Status:** ready-for-review · **Owner:** Gemini · **Branch:** task/NEX-133 · **Depends on:** NEX-127 (agent files first)
**Requirements:** P04, P18, DM-8, M01, M83, D22, D58, D60, D61, V-1, V-2, V-6, V-7, D57; Control side is NEX-134

## Goal
A cell's agent can run three signed commands for one tenant: `tenant.freeze` (no more writes, reads still work),
`tenant.export` (NXTE/1 encrypted for a public key the institution supplied) and `tenant.destroy_keys`
(crypto-shred: every key destroyed, encrypted data unreadable for good). Each reports ids and counts only.

## Build
1. `0022`: `tenants.frozen_at` (nullable). Frozen = every write to that tenant's data is refused with 423
   `tenant_frozen` by one shared guard (API writes and workers), reads and the export keep working. Owner role only
   sets it; the app role cannot clear it.
2. `tenant.freeze` (args `{tenantId}`): sets `frozen_at` once (repeat = no-op); audit `m01.tenant.frozen`.
3. `tenant.export` (args `{tenantId, recipientPem}`): only a frozen tenant (else `failed: not_frozen`); runs the
   NEX-106 export for that PEM (RSA ≥ 3072, refused otherwise); result `{fileName, bytes, pemSha256, tables, rows}`.
   The file stays in this cell's export folder; it never goes to Control (D61).
4. `tenant.destroy_keys` (args `{tenantId, exportPemSha256}`): only a frozen tenant whose latest export matches that
   fingerprint (proof an export exists, else `failed: no_export`); runs `destroy_tenant_keys`; result
   `{keyIds, destroyedAt}`. Irreversible: the command must also carry `approvedBy` with two different staff ids
   (checked again here; else `rejected`).
5. All three: `install_mode` `saas` only (self-hosted installs offboard themselves); tenant must exist; no people.
