# NEX-143 — Control: one open offboarding or move per tenant (D66)

**Status:** done · **Owner:** Gemini · **Branch:** task/NEX-143 · **Depends on:** NEX-141, NEX-142
**Requirements:** D61, D63, D66, P04, P18, V-2; follow-up of the NEX-141 / NEX-142 reviews

## Goal
Control refuses to start (or retry) an offboarding or a move for a tenant that already has one open, so two jobs can
never freeze, export or destroy the same tenant's keys at once; staff see a clear message in both start dialogs.

## Build
1. `tenant_jobs.py`: `async def ensure_no_open_job(conn, tenant_id, *, except_offboarding=None, except_move=None)`
   takes `pg_advisory_xact_lock(hashtext('tenant-job:' || tenant_id))`, then raises `ApiError(409, "conflict",
   "This tenant already has an offboarding or move in progress.")` if any `offboarding_jobs` or `portability_jobs`
   row for the tenant has status `pending` or `running` (other than the excepted ids). A `failed` job does not block.
2. Call it inside the transaction of `POST /offboarding-jobs`, `POST /portability-jobs`,
   `POST /offboarding-jobs/{id}/retry` and `POST /portability-jobs/{id}/retry` (excepting the job itself), before any
   command is queued. The offboarding a move's `cutover` inserts is not a new start: leave that path unchanged.
3. Log job ids, tenant id and `outcome=busy` only.
4. Mocks: the same rule on create and retry (409). Dialogs: on a 409, **Start offboarding** shows
   `p04.off.form.busy` and **Start move** shows `p18.form.busy` ("This tenant already has an offboarding or move in
   progress.") instead of the general failure text; both with `hi` / `ta` and translator descriptions.
5. `API.md`: the four rows say `409` when another job is open. `CONTROL-GUIDE.md`: one line under Provisioning and Moves.
