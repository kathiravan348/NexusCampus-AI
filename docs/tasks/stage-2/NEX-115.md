# NEX-115 — Control: P07 releases and rollouts on real data, and the agent's online update check

**Status:** ready-for-review · **Owner:** Gemini · **Branch:** task/NEX-115 · **Depends on:** NEX-113

## Goal
Control serves `GET /releases`, `/rollouts` from its database (as the mocks), and an install asks
`GET /control/api/v1/agent/update` with its agent token to learn which published release it may move to.

## Build
1. `c0007_releases`: `releases` (every Release field; checks mirroring the contract's refines; `version` unique per
   channel) and `rollouts` (every Rollout field, `deployment_ids` text[], FK `release_id`, ring 0–3, unique
   (release_id, ring)). Grant SELECT only to `control_app` — publishing and rollout start stay in the mocks here.
2. Export `releases` and `rollouts`; fixtures version 6 in `export.ts` and `seed.py`; seed after deployments.
3. `releases.py`: Resources `releases` and `rollouts` with `ctl.release.read` and the mocks' filters and keys.
   Neither table has `account_id`, so partner viewers see none (the NEX-113 rule).
4. In `fleet.py`, move the token check of `POST /agent/health` into one reusable dependency (bearer → SHA-256 lookup →
   revoked / unknown → the same 401) that returns the deployment row; health check-in uses it unchanged.
5. `GET /control/api/v1/agent/update` (agent token, no body, no cookie): the offer is the newest **published**,
   **signed** release on the deployment's channel that is newer than its version (`version_key` order, pre-releases
   only on `preview`), whose `minUpgradeFrom` ≤ its version, and where a rollout of that release with status
   `running` or `done` lists this deployment. Answer `200 {"release": Release}` or `200 {"release": null}`.
   Air-gapped deployment → 403. Max 1 request per 60 s per deployment → 429 (keep the last time in memory or a
   column; say which in the handoff). Log deployment id and outcome only.
