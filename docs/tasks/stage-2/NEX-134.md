# NEX-134 — Control: P04 offboarding for real (D61) — four-eyes key destruction and a signed shred certificate

## Goal
Staff run an offboarding job step by step: freeze, export for the institution's key, confirm the institution has
the file, destroy the keys only after a second staff member approves, then Control issues a signed shred
certificate anyone can check against our published public key.

## Build
1. `c0019`: `control_app` INSERT / UPDATE (`steps`, `status`, `shred_certificate_id`) on `offboarding_jobs`, INSERT on
   `shred_certificates`; internal columns: recipient PEM fingerprint, export result, first and second approver.
2. `POST /offboarding-jobs` (`ctl.provisioning.manage`; `{accountId, tenantId, recipientPem}`; RSA ≥ 3072): tenant
   on the account and in a cell; queues `tenant.freeze`. Results move steps: `freeze_writes` → done, then queues
   `tenant.export` with the PEM → `export_ready`.
3. `POST /offboarding-jobs/{id}/confirm-download` (staff confirms the institution received the file) →
   `export_downloaded`.
4. `POST /offboarding-jobs/{id}/approve-destroy`: the first call records approver 1; a call by a *different* staff
   member records approver 2 and queues `tenant.destroy_keys` with both ids and the export fingerprint; the same
   person twice → 409. Before `export_downloaded` → 409.
5. On the destroy result: build the certificate `{id: shr-…, tenantId, keyIds, destroyedAt}`, sign its canonical JSON
   with Transit `nexus-shred` (Ed25519, never exported; 88-char signature, `signingKeyId` = `nexus-shred:vN`), store
   it, set `keys_destroyed` and `certificate_issued`, job `done`. `GET /shred-certificate-keys` (no auth) returns the
   public keys so a certificate can be checked offline.
6. Every step in one transaction with the job row locked; log job id, step, staff ids, outcome — never the PEM.
