# NEX-205 — Build: DB + API for M17 attendance (sessions, roster, marks, leave requests; offline replay)

**Status:** planned · **Owner:** — · **Branch:** task/NEX-205 · **Depends on:** NEX-187 (migration chain, slots)
**Requirements:** M17, G-3, G-6, V-1, V-2, V-7, O-2, D78, D80. Split from NEX-187 (D83 planning).

## Goal
Attendance sessions, marks and leave requests are stored per tenant under forced RLS and served by the real backend
with the same responses, errors, masking and order as the mock. Marks are append-only and safe to replay from the
offline outbox (`Idempotency-Key`, core guard). Notes and leave reasons are personal data: encrypted, never logged.

## Build
1. Migration `0032`: `attendance_sessions`, `attendance_marks`, `leave_requests`; columns as the contract (snake_case);
   composite `(id, tenant_id)` references (institutions, class groups, timetable slots, staff role profiles, learners,
   people, sessions). CHECKs for every contract rule (slot iff `period`, label iff `event`, `submitted_at` iff not
   open, minutes late iff `late` and 1–600, `to >= from`, decided fields iff approved / rejected, enums). `note` and
   `reason` stored as FieldCipher text (`attendance_marks.note`, `leave_requests.reason`, `tenant_data` key).
   ENABLE + FORCE RLS, `tenant_isolation`; `nexus_app` SELECT on all three, INSERT on `attendance_marks` only.
2. Reads as the mock: `GET /attendance-sessions?classGroupId=` (`m17.attendance.read`, staff only, `404` unknown
   group); `/:id/roster` (staff only; active placements on the session date, roll number order, one row per learner);
   `/:id/marks` (module only: staff with read see all, others only their family's learners or `403`; `note` null
   without `m17.attendance.mark`); `GET /leave-requests` (`m17.leave.decide` sees all; staff without it `403`;
   family sees its learners). Reading a decrypted note or reason records one `m17.*.sensitiveRead` event (E-3).
3. `POST /attendance-sessions/:id/marks` in the mock's order: module → `m17.attendance.mark` → active staff profile
   on today's date (`403`) → session (`404`) → closed session `409` path `status` → body `400` (path = first key,
   "Invalid attendance mark") → learner outside roster `400` path `learnerId` → insert (`method: manual`,
   `deviceId: null`) → `201`. Audit `m17.attendanceMark.created` (field names only; `note` marked sensitive).
4. Tests (real DB): every route, filter, masking and `403` branch; roster order and dates; mark create + replay with
   the same `Idempotency-Key` returns the same mark and one audit row; closed session; roster check; note and reason
   stored as ciphertext and in `ENCRYPTED_COLUMNS`; sensitive-read audit; tenant B isolation; forced RLS + grants;
   models match the schema.
