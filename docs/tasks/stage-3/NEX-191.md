# NEX-191 — Build: DB + API for M24 messages, notices and meetings

**Status:** planned · **Owner:** — · **Branch:** task/NEX-191 · **Depends on:** NEX-184, NEX-190 (migration chain)
**Requirements:** M24, G-6, V-1, V-2, V-7, O-2, D78, D80

## Goal
Message threads and messages, notices, meeting slots and bookings are stored per tenant under forced RLS and served by
the real backend with the same responses, errors, visibility and order as the mock. Replies are safe to replay from
the offline outbox. Message bodies and booking notes are personal data: encrypted, never logged.

## Build
1. Migration `0038`: `message_threads` (participants ≤ 500 distinct, ≥ 2 unless broadcast, class group iff
   `class_group`), `thread_messages` (encrypted `body`, attachment and reader arrays, `edited_at >= sent_at`),
   `notices` (audience JSONB, 1–5 distinct channels, `expires_at > publish_at`), `meeting_slots` (`HH:MM`,
   `end > start`, capacity 1–10), `meeting_bookings` (encrypted `note`). Composite `(id, tenant_id)` references.
   ENABLE + FORCE RLS, `tenant_isolation`; `nexus_app` SELECT on all; INSERT on `thread_messages`; `UPDATE
   (last_message_at, updated_at)` on `message_threads` only.
2. Reads as the mock: threads where the viewer is a participant; a thread's messages (`404` when not a participant;
   bodies decrypted, one `m24.threadMessage.sensitiveRead` per page); notices (`m24.notices.publish` sees all, others
   only published, live and addressed to them by everyone / their family's active class groups / their system role
   key / their person id); meeting slots (`?staffProfileId=`, `404` unknown); bookings (`m24.meetings.manage` all;
   otherwise own guardian bookings with note and bookings on the viewer's staff slots with note null).
3. `POST /message-threads/:id/messages` in the mock's order: module → `m24.messages.send` → thread of the viewer
   (`404`) → archived `409` (path `archived`) → body `400` (path of the issue, `body` when none, "Invalid message
   body") → insert (sender = viewer, read by the sender, `deviceId` null) and set the thread's `lastMessageAt` →
   `201`. Audit `m24.threadMessage.sent` (`body` marked sensitive). Replay via the core `Idempotency-Key` guard.
4. Tests (real DB): each read and its visibility rule, notice audiences and time windows, booking masking, reply,
   archived `409`, bad body, replay, ciphertext and `ENCRYPTED_COLUMNS`, sensitive-read audit, tenant B isolation,
   forced RLS and grants, models.
