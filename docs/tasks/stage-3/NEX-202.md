## Build
1. Migration `0027`: `households` (address JSONB nullable, `learner_person_ids` / `guardian_person_ids` arrays with
   the contract's size and uniqueness limits), `guardian_relationships`, `authorised_pickups`; columns as the
   contract (snake_case); composite `(id, tenant_id)` references to `people` for every single person id; check
   constraints for the contract's rules (guardian ≠ learner, `effective_to >= effective_from`, `valid_to >=
   valid_from`, note present exactly when `pickup_right = 'court_restricted'`). `court_order_note` stored only as
   `FieldCipher` text bound to its column. ENABLE + FORCE RLS, `tenant_isolation`, `nexus_app` SELECT only.
2. Routes (module `M14`): `GET /households`, `/guardian-relationships?learnerPersonId=`, `/authorised-pickups?
   learnerPersonId=` (paged). Scope as the mock: `m14.family.read` sees all learners of the tenant; otherwise only
   learners in `family_of(viewer)`, none → `403 forbidden`; a `learnerPersonId` outside the scope → `404`.
   Households: those with at least one learner in scope. Without `m14.family.read_restricted` →
   `courtOrderNote: null` (never decrypted for that viewer); `pickupRight` stays visible.
3. E-3: when a decrypted court-order note is returned, record one audit event per request,
   `m14.guardianRelationship.sensitiveRead` (target learner person id, or `guardianRelationshipList`; field names
   only, no values) in the request transaction.
4. Register `guardian_relationships.court_order_note` in `ENCRYPTED_COLUMNS`.
5. Tests (real DB, as `tests/db/m13`): routes, paging; read vs restricted; guardian: own child only, other `404`, no
   family `403`; ciphertext in table, plaintext only with restricted access; audit only when a note is shown;
   tenant B isolation; forced RLS on all three tables; models match the schema; an export row decrypts.

## Questions
- For a tenant-wide reader, should `GET /households` include a household whose learner person IDs have no matching M13 learner row? The frozen mock includes it via `canReadAll`. Build item 2 requires at least one learner in scope, which would exclude it.
  - answered by the planner: follow the mock. A viewer with `m14.family.read` sees every household of the tenant, including ones whose learner ids have no M13 learner row; "at least one learner in scope" applies only to family-scoped viewers.
- May I read `frontend/packages/contracts/src/tenancy.ts` and `frontend/packages/contracts/src/common.ts` for the address and shared field definitions imported by `families.ts`? The task’s read list omits both.
  - answered by the planner: yes — read both (and any other contract file `families.ts` imports); they are frozen, do not change them.

- Review 2: May I inspect the existing backend locale validators, earlier locale-related migrations and `backend/pyproject.toml` for the project’s canonical BCP 47 implementation? The current schema and database check reject malformed or wrongly cased tags, but accept `iw-IL`, which the frozen `Intl.getCanonicalLocales` rule canonicalises to `he-IL` and therefore rejects. The listed backend files expose no equivalent canonicaliser.
  - answered by the planner: yes, read them. The project's canonical check is `nexus.core.validation.is_locale` (shape only — Python has no `Intl`); M01 uses it via `check(...)`. Use it (replace the local `Locale` regex) and keep the database check as the same shape. Deprecated aliases such as `iw-IL` are an accepted known gap, as in M01: do not add a canonicaliser, alias table or new package, and do not test `iw-IL`.
