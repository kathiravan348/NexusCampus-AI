# NEX-181 — Menu shows only screens the user can open (role-profile audience, D77)

**Status:** planned · **Owner:** — · **Branch:** task/NEX-181 · **Depends on:** NEX-160–178
**Requirements:** V-1 (deny by default), G-1, D77; M13, M14, M18, M21–M23, M25–M27; `AGENTS.md` §9

## Goal
Every menu link opens a screen for that user. Today modules with `permission: null` show in every menu, and the mock
API then answers 403 ("No access"), e.g. admin → `/family`, teacher → `/fees`, guardian → `/staff`, `/learner`;
learner → `/families` (404s for a sibling's pickups). Found by the NEX-179 persona smoke (`e2e/personas.spec.ts`).

## Build
1. `audience?: { readonly kinds: readonly RoleProfileKind[]; readonly notStaff?: boolean }` (type from
   `@nexus/contracts`). Doc comment: the entry is permitted when the user holds `permission`, **or** has an `active`
   role profile in the current tenant whose `kind` is in `kinds` (and, with `notStaff`, no active `staff` profile).
   An entry with `audience` and `permission: null` is permitted only through `audience`. No `audience` → unchanged.
2. Values (permission · audience):
   - M13 `learners`: `m13.learner.read` · guardian, learner, notStaff
   - M14 `families`: `m14.family.read` · guardian, notStaff
   - M18 `fees`: `m18.fees.read` · guardian, learner, notStaff
   - M21 `exams`: `m21.exams.read` · M22 `report-cards`: `m22.reports.read` · M23 `documents`:
     `m23.documents.read` — each · guardian, learner, notStaff
   - M25 `family`: `null` · guardian · M26 `learner`: `null` · learner · M27 `staff`: `null` · staff
   - M24 `messages` stays `permission: null`, no audience (every role holds the M24 read codes).
3. Menu and route use the same `isPermitted` (no second rule); a hidden entry's URL shows `Forbidden` as today.
4. Do not change screens, handlers, fixtures or contracts. If a rule above contradicts a handler, write it under
   `Questions` (`- ` line) and stop.

## Questions
- M18, M21, M22 and M23 use `familyLearnerIds`, which rejects any staff profile in the tenant. The specified `notStaff` rule ignores inactive staff profiles. An active guardian with an inactive staff profile and no module read permission would see a link that returns 403. Which staff-profile rule should both gates use?
  (answered by the planner 2026-11-25) Mirror the handler, do not change it: `notStaff` means **no `staff` profile
  of any status** in the current tenant (same as `isStaff` in `m18.ts`). The `kinds` match still needs an `active`
  profile. Hiding a link the handler would serve is fine (deny by default); showing one that answers 403 is not.
- M25–M27 would show a portal for each matching active profile. M28’s `roleHome` returns a single role, in priority order (dashboard reader, staff, guardian, learner), and does not filter inactive profiles. For example, a staff member with dashboard read permission gets a leader home, and a staff member who is also a guardian gets no family home. Should portal visibility follow the single role returned by the handler, or should the handler support each active profile?
  (answered by the planner 2026-11-25) Follow the single role `roleHome` returns (the portal screens show
  `Forbidden` when `home.role` differs; handlers stay unchanged). Add to `audience` two more optional flags, same
  "any status" reading as `notStaff`: `notGuardian` (no `guardian` profile) and `notLeader` (user lacks
  `m28.dashboards.read`). Values: M27 `staff` · kinds staff, notLeader · M25 `family` · kinds guardian, notStaff,
  notLeader · M26 `learner` · kinds learner, notStaff, notGuardian, notLeader. Acceptance: also test a staff + guardian
  user (sees M27, not M25) and a user with `m28.dashboards.read` (no M25–M27). The admin persona therefore sees no
  M27; update the USER-GUIDE line to say a leader's home is the dashboard.
- An active guardian profile grants the Fees link under the specified audience rule. For the same guardian without `m18.fees.read` or a linked learner in this tenant, `familyLearnerIds` returns 403. M21–M23 use the same check, and M13/M14 also require a matching learner for family access. Is a linked learner guaranteed for every active guardian in this prototype, or which tenant-scoped signal should the guard use to hide these links?
  (answered by the planner 2026-11-25) Keep the rule as specified: the guard uses only `/me` data (no extra fetch,
  no fixture change). The menu is a convenience, not the access boundary — the handler still denies (V-1). An active
  guardian with no linked learner in the tenant is an incomplete record; its screens show `Forbidden` / "No access",
  which is acceptable. The demo personas all have linked learners; the reviewer proves it with `pnpm e2e` (NEX-179).
